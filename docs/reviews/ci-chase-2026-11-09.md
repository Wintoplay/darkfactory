# The CI-chase loop (2026-11-09)

A dependency refresh was finished in the morning. The report did not go out for
hours, because three unrelated test failures were chased one at a time, each
with a full CI round trip. This doc records the cost structure and the rules
that stop it from repeating.

## What the refresh needed

Eleven commits: a Go/Wails bump, Dependabot configuration, an Android toolchain
migration (AGP 9.5.1, Gradle 9.9.0, SDK 36), a `versionCode` fix in two places,
a session `Stop` verdict fix, and an attach-seam fix. Two of those — `Stop` and
the attach seam — were real product bugs that CI surfaced. The rest was the
task.

## Where the time went

- **Eight or so full CI cycles, run serially.** Each push starts `ci`,
  `protocol security` and `vuln`; the critical path is 5–6 minutes. Waiting for
  green before the next push turned three independent defects into a chain.
- **`make check` twice per fix**, once before and once after, at ~4 minutes
  each. Half of that was redundant; targeted package tests answer the same
  question while iterating.
- **A force-push to delete a wrong `Co-Authored-By` trailer**, which cost one
  more full cycle. The trailer should never have been written, and a public
  `main` should not be rewritten to fix a message.
- **The investigations themselves were not the problem.** The 3000-iteration
  race run and the seam test with a deliberately injected scheduling gap are
  what made the two real fixes provable. That work is the part worth keeping.

## Rules

1. **Batch findings.** While CI runs, keep fixing locally. Push one commit per
   batch, not one per discovery.
2. **Targeted while iterating, full once.** `go test -race -run Name ./pkg` and
   the seam/race loops are for development; `make check` is the pre-push gate.
3. **Classify a flake before chasing it.** Rerun the failed job once. If it
   passes and leaves no evidence, add the evidence (visible UI, timings) and
   move on; investigate only when the failure is reproducible, has a plausible
   mechanism, or recurs.
4. **Do not block the report on an unrelated failure.** Report the task's state
   and name the open item; the fix can land on its own cycle.
5. **Publish attribution truthfully.** Never add a `Co-Authored-By` for a model
   or tool that did not write the change. To correct a published message, add a
   follow-up commit; rewriting public history needs the owner's agreement.
6. **Separate the refresh from the bug hunt.** A dependency task that turns into
   two correctness fixes is two reports, not one long silence.

## Evidence kept

- `internal/session/session_test.go`: 3000 race iterations of the stop verdict.
- `internal/session/subscribe_test.go`: 200 attaches across a numbered stream;
  fails on the first iteration when a 2 ms gap is restored to the old shape.
- `test/security/android_acceptance.py`: a timed-out wait now prints the
  visible UI, so the next emulator failure explains itself.
