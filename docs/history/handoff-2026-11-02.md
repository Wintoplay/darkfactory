## Current handoff: native Android shell, E2EE, multi-host, and remote-UI boundary (2026-11-02)

The remote browser UI is now a refused surface. The daemon serves `/`,
`index.html`, and static assets only to a loopback peer with a loopback Host and
no forwarding headers; remote `/api/v1/...` remains for a native client. The
Wails shell and local browser still load one daemon UI and are local-only.

The first native Android client is in `android/`, written in Kotlin:

- native pair screen and `POST /api/v1/pair`; the client sends a P-256 public
  key and receives a sealed per-device token, the daemon host public key, and a
  fingerprint;
- the desktop QR is a `darkfactory://pair?base=…&code=…` deep link that
  prefills the native pair form through the phone camera; the URL/code form is
  still the fallback;
- one Android Keystore-backed AES-GCM registry for several hosts, each with its
  own endpoint, token, device id, client key, pinned host key, fingerprint,
  scope, and stable `hostId`;
- a native picker to connect, add, or forget a host; one host is connected at a
  time, and a switch destroys the previous loopback origin and WebView;
- bundled `web/` assets copied at build time;
- a per-launch random `*.localhost` origin, bound to `127.0.0.1`, that serves
  those assets;
- a native `POST /api/v1/e2ee` envelope for every API call: P-256 ECDH +
  HKDF-SHA256 + AES-GCM; request bodies, bearer token, response headers, and
  PTY/OpenCode bytes are encrypted, and streams are framed;
- a per-host key pin and a fingerprint confirmation dialog; the desktop Pair
  phone dialog shows the same fingerprint. A changed key removes only that host
  and opens a prefilled pair form.
- WebView lockdown: no JavaScript bridge, no file access, no cookies, no mixed
  content, local-origin navigation only;
- logout, `401`, or AEAD failure removes the current host and returns to the
  picker or pair; other hosts stay saved. A local WebView stream abort is not
  treated as a host failure.

## Previous handoff: device-key auth (2026-11-01)

The trusted-HTTPS branch is **superseded**. WebKitGTK rejects the daemon's
Secure `__Host-` cookie over plain loopback, but a system CA install needs sudo
and was blocked. The user chose device-key auth (Orca-style). It needs no
sudo, no system trust change, no TLS listener, and no native auth bridge.

### Implemented

- `store.DeviceKey` in a separate bucket: ES256 SPKI public key, label, scope,
  terminal, created/last-seen/expiry, and `SecretTag`. The private key never
  leaves the client.
- `POST /api/v1/device-keys` is an authenticated mutation (`device.key.create`)
  that inherits the caller's scope and terminal opt-in.
- `POST /api/v1/device-keys/challenge` and `/verify` are unauthenticated
  bootstrap routes with same-origin, `X-DF-Request`, and rate-limit checks.
  The challenge is 32 random bytes, one-use, 120 s. The signature is raw ES256
  `r||s` over `darkfactory-device-auth-v1\n<device-id>\n<challenge>`; verify
  re-reads the key under the lock so a concurrent revoke cannot mint a session.
- Verify returns a 12-hour in-memory session bearer; `authenticate` accepts it
  as `authSession`, and read-only/terminal checks apply. No cookie is set.
  Logout ends only that session; revoking a key deletes it and all its sessions.
- The client generates a non-extractable ECDSA P-256 key after the first token
  login, stores the `CryptoKey` in IndexedDB, registers the public half, and
  auto-signs on every later launch or lost 401. It clears the local key only on
  a challenge `401`, not on a verify failure (the nonce may have expired).
- Devices lists keys with `kind: "key"`; `current` works for a key session;
  revoke uses the existing endpoints.
- Secure/`__Host-` cookies, CSP, `sessionStorage`, terminal opt-in, and the
  master-token boundary are unchanged.

## Resolved: clicking the OpenCode TUI inside xterm

The user's reports:

> "I still cannot click ... cannot click opencode sessions"
> "Continuing ongoing work session in opencode still cannot be clicked. I mean
> within the term itself. and it feel slow. Have you enabled GPU?"

This was the **PTY terminal**, not the DOM Chat panel. The root cause is proven,
not a hypothesis: the session host owns the PTY and tracks its input modes, but
its attach snapshot carried only the ring tail. OpenCode's TUI enables
`?1000/1002/1003` and `?1006` once at startup; after a few MB of paint that
enable is evicted from the 4 MiB ring. A restarted `darkfactory serve` seeded
its mode tracker from that tail, so `modes.Restore()` was empty, the fresh
xterm had mouse reporting off, and clicks became text selection.

Live proof before the fix: the running session's ring was exactly 4,194,304
bytes with **zero** mouse enables and 9,818 `?25l` / 9,819 `?25h` repaint pairs;
the daemon had restarted two hours after the TUI started.

**Fix:** `internal/session/host.go` appends `sess.modes.Restore()` to the
snapshot frame on attach. No new frame kind: an older daemon already seeds its
tracker from those bytes, so the host stays wire-compatible. Regression test
`TestHostReattachRestoresEvictedModes` evicts the enable, detaches the daemon,
reattaches a fresh `Manager`, and requires the redraw replay to restore the
modes; it fails without the append. Activated live on 2026-11-01 13:42 +07;
the browser replay now starts `\x1b[0m\x1b[?1006h\x1b[?1003h\x1b[?2004h`
with `X-DF-Redraw: 1`. Full evidence:
`test/artifacts/client-foundation/tui-mode-restore/evidence.txt`.
A live `?debug=1` attach at 1280×900 reports `mouse=any` in xterm for both
running sessions.

`?1003` is restored, not `?1000`: the tracker keeps the last of
`?1000/1002/1003` as one family, and any-event tracking still reports clicks.
The DOM Chat panel remains the intended OpenCode surface; the TUI is for shells
and other PTYs, but it must not silently lose mouse input after a restart.

**Desktop renderer decided by evidence.** Chromium/Blink and non-Linux WebKit
load the WebGL2 addon; WebKitGTK (the Wails shell on Linux) keeps the DOM
renderer. The addon logs its GL string behind `?debug=1`, falls back to DOM
for a software context, and skips a fractional DPR. In headed Chromium on the
Intel GPU, three alternating trials gave a median final render of 550.8 ms
with WebGL vs 577.9 ms with DOM (about 5%, synthetic parse burst). In
Wails/WebKitGTK the same burst parsed in ~3.57 s vs ~0.55 s in Chromium; WebGL
had no reliable win (3.6–21.0 s final vs 3.6–8.6 s DOM), so the shell stays on
DOM. The fixture writes serially; the app coalesces per frame, so the parse gap
is a signal to measure real echo latency, not app latency. Full numbers and raw
runs: `test/artifacts/client-foundation/desktop-webgl/`. A live browser check at
1280×900 reported the Intel ANGLE renderer and `mouse=any` on both sessions.
